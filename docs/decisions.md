# Build decisions

Decisions taken during the build where the brief was open or the environment forced a choice. Newest at the bottom of each section.

## Process
- Work happens in phases. Each phase gets its own branch (`phase/N-name`) and PR into `main`, and must pass CI and a review before merging. Merges are squash merges.
- Phases: 1 scaffold, CI and deploy. 2 brand and layout shell. 3 engine (tax, model, defaults) and data pipeline. 4 calculator UI. 5 area and nation pages, content pages, SEO. 6 accessibility, performance and end-to-end hardening.

## Hosting
- Until a custom domain is registered, the site is served from GitHub Pages at `https://jordanl17.github.io/HouseSums/`. Astro's `site` and `base` come from env (`SITE_URL`, `BASE_PATH`) so moving to `housesums.co.uk` is a config change. All internal links must go through the base path helper. Never hard-code `/HouseSums`.
- Package manager: npm. Node 22 (`.nvmrc`).
- Fonts are self-hosted via `@fontsource/b612` and `@fontsource/b612-mono`. No runtime font CDN.

## Defaults and outlook presets
Users asked to be able to choose between more cautious and more optimistic outlooks. The calculator has an **Outlook** control with three presets. Picking one sets the four economic assumptions below. Every value can still be edited individually afterwards, and the preset shows as "Custom" once one is changed. All preset values live in `data/defaults.json`, not in code.

| Assumption | Cautious | Typical (default) | Optimistic |
|---|---|---|---|
| House price growth | lower of area 10-year average and 1.5% | area 10-year average, clamped 0-6% | area 10-year average + 1 point, capped at 6% |
| Rent increases | lower of area rent growth and 2% | area rent growth, clamped 1-6% | area rent growth, clamped 1-6% |
| Investment return | 3.5% | 5% | 6.5% |
| Rate after fix | initial rate + 0.5 points | same as initial rate | initial rate - 0.5 points |

- Typical matches the brief exactly, and all model test cases in the brief run against Typical.
- The brief's open questions on the growth cap (kept at 0-6%) and investment return (kept at 5%) are resolved by making Typical match the brief and offering Cautious as the alternative.

## Data
- The build container cannot reach ONS, HM Land Registry or the Bank of England. Data is fetched only by the `refresh-data` GitHub Action. No figures are ever typed in by hand. Phase 3 replaced the labelled samples with the first real snapshot (361 local authorities, from Actions run 38421635252); see "Data pipeline (phase 3)". The `sample` flags stay in the schema, and the UI shows a notice only if a file ever carries `"sample": true` again.
- The refresh workflow pushes a branch and opens a PR. If GitHub Actions isn't allowed to create PRs in this repo, it pushes the branch and the PR is opened manually.

## Analytics
- GoatCounter, loaded only when `PUBLIC_GOATCOUNTER_CODE` is set at build time. Off until Jordan creates an account. Events are named in `src/lib/analytics.ts` and never include input values.

## Tooling (phase 1)
- **Preact 10, not 11.** `@astrojs/preact` 6.0.6 (the latest) declares `preact@^10.6.5` as a peer, so Preact 11 fails `npm install` with a peer conflict. We use the latest Preact 10 and move to 11 when the integration supports it. No `--legacy-peer-deps`.
- **TypeScript 6.0.** TypeScript 7 is out, but `typescript-eslint` supports `<6.1` and `@astrojs/check` supports `^5 || ^6`. Pinned to `~6.0.3`.
- **Playwright pinned to 1.56.1.** It is the release whose Chromium build (1194) matches the browser preinstalled in the build container at `/opt/pw-browsers`, so local runs need no download. CI installs the matching Chromium with `npx playwright install --with-deps chromium`. Upgrade Playwright only together with the container's browser.
- **Trailing slashes: always.** `trailingSlash: 'always'` with `build.format: 'directory'`. Pages build to `folder/index.html`, which is what GitHub Pages serves, and canonical URLs end in `/`. `url()` in `src/lib/url.ts` adds the slash to page paths and leaves file paths (anything with an extension) alone. Note that `astro preview` returns 404 for a path without its trailing slash, where GitHub Pages would redirect.
- **Base path default applies everywhere.** `BASE_PATH` defaults to `/HouseSums` in dev, build and preview alike, so local URLs match production. Set `BASE_PATH=/` for a custom domain.
- **Prettier skips Markdown.** Docs are hand-written prose and the brief is the source of truth; reformatting their tables would create churn. Code, config, CSS and Astro files are formatted.
- **ESLint 10 flat config** with `typescript-eslint` recommended, `eslint-plugin-astro` recommended and `eslint-config-prettier` last. `npm run lint` runs `eslint .` then `prettier --check .`; `npm run format` is the only command that changes files.
- **Strictest TypeScript.** `tsconfig.json` extends `astro/tsconfigs/strictest` (adds `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes` and friends on top of `strict`).
- **Astro telemetry is turned off in CI** with `ASTRO_TELEMETRY_DISABLED=1`.
- The Preact renderer's client files (about 23KB raw) are emitted into `dist/_astro/` even while no page uses an island. They count towards the 100KB budget, but no page loads them yet.
- **GitHub Actions pinned to major tags** (checked October 2026): `actions/checkout@v7`, `actions/setup-node@v7`, `actions/configure-pages@v6`, `actions/upload-pages-artifact@v5`, `actions/deploy-pages@v5`, `actions/upload-artifact@v7`.
- **CI runs on every pull request and on pushes to any branch.** A branch with an open PR therefore gets two runs (one `push`, one `pull_request`). The concurrency group is keyed on the ref, so the two do not cancel each other, but a newer push cancels an older run of the same kind.
- **The deploy workflow builds and runs the JS budget but not the full test suite.** It relies on CI having passed on the same push to `main`.
- **GitHub Pages must be switched on by hand once** (Settings, Pages, Source: GitHub Actions). `configure-pages` with `enablement: true` cannot do it with the default `GITHUB_TOKEN`; it needs a PAT or GitHub App token, which we do not want to store. Done: Jordan made the repository public and switched Pages on, and the site is live at `https://jordanl17.github.io/HouseSums/` (fact updated in phase 6).
- **JS budget:** `scripts/check-budget.mjs` counts raw bytes of every `.js`/`.mjs`/`.cjs` file in `dist/` (not gzip), including the Preact renderer chunks no page loads yet. Limit 102400 bytes. `--max-bytes` and `JS_BUDGET_BYTES` exist for experiments only; CI uses the default.
- **Playwright's webServer runs `astro preview --ignore-lock`** on port 4322 at 127.0.0.1. Without the flag, Astro 7 moves preview to the background when it detects a coding agent, and Playwright sees the command exit early. If you run plain `npm run preview` from an agent session it starts in the background; stop it with `npx astro preview stop`.
- **`url()` edge cases:** a bare `//` or `///path` (no host) is treated as an internal path, and repeated slashes inside the base are collapsed. `//host/path` is still treated as external and returned unchanged.

## Deploy gate and live tests (phase 1 gate)
- `deploy.yml` calls `ci.yml` first (`workflow_call`) and only builds and deploys if the whole CI suite passes. `ci.yml` no longer runs on pushes to `main`, so each main commit is checked once, by the deploy run.
- After every deploy, a `live` job runs the full Playwright suite against the real GitHub Pages URL (`npm run test:live` with `LIVE_URL`). `scripts/wait-for-deploy.mjs` first waits until the live page's `<meta name="hs-build">` matches the commit, so the tests never hit the previous deploy in the CDN. A red deploy run means production is broken. Fix it before starting anything else.
- e2e tests must therefore work against both `astro preview` and the live site: navigate with relative paths and don't depend on local-only behaviour.
- Permissions are per job: only the deploy job gets `pages: write` and `id-token: write`. Checkouts use `persist-credentials: false`.

## Design system (phase 2)
- **Files and load order.** `src/layouts/Base.astro` imports, in this order: the four `@fontsource` latin CSS files (B612 400/700, B612 Mono 400/700; B612 Mono has a 700 weight, so we ship it), `src/styles/tokens.css`, `src/styles/base.css`, `src/styles/ui.css` (UI primitives, one file per primitive in `src/styles/ui/`), `src/styles/shell.css` (skip link, header, logo, nav, footer). All of it is global CSS bundled by Astro into one stylesheet. No CSS framework, no client JS.
- **Tokens are the only place colours live.** `src/styles/tokens.css` holds every colour (brief values, light by default, dark under `prefers-color-scheme: dark`), plus spacing (4px base, `--space-1` = 4px up to `--space-16` = 64px), radius (`--radius-card` 26px, `--radius-pill` 999px), type families and scale (`--size-xs` to `--size-2xl`, `--size-answer` for the answer numeral only), focus and layout tokens, and the contour background (`--contour-background`). `scripts/check-tokens.mjs` (run by `npm run lint`) fails on any hex, `rgb()`/`hsl()`-style function or named colour in any `.css`, `.astro`, `.tsx` or `.jsx` file, or `.ts`/`.js` under `src/`, outside tokens.css. CSS system colours (`Canvas`, `CanvasText`...) are allowed for forced-colours mode. A line containing `check-tokens-ignore` is skipped; use it only with a reason.
- **Class naming: BEM-lite, global, no scoped styles for shared UI.** `.block`, `.block__element`, `.block--modifier`, lower case and hyphenated: `.field`, `.field__input`, `.field--invalid`, `.tag--local`, `.button--secondary`. State uses native attributes where they exist (`:checked`, `[open]`, `[aria-invalid="true"]`, `:disabled`) rather than `.is-*` classes. Utilities are single words: `.container`, `.stack`, `.visually-hidden`, `.mono`, `.tabular`, `.num`, `.muted`, `.prose`. Primitives and shell styles are global (not Astro `<style>` blocks) so the phase 4 Preact components can reuse them by class name. Page-only tweaks may use a scoped `<style>` in the page.
- **Focus ring.** Hi-vis alone is about 1.2:1 against light concrete, so the focus indicator is a 3px hi-vis ring (a `box-shadow` filling the outline offset) inside a 2px `#1A1A1A` outline (`--color-focus-edge`, the same in both themes). In light the ink outline gives the 3:1 against concrete and surface; in dark the hi-vis ring gives it against dark concrete and surface. Forced-colours mode drops the shadow and keeps the outline. It is applied globally to `:focus-visible`; components whose real control is visually hidden (segmented radios) draw it on the visible sibling with the same tokens or the `.focus-ring` class.
- **Contour background** is applied to `body` with `background-attachment: fixed`, so there is one set of circles per view, centred at 85% 12% of the viewport, and the circles do not restart per section. Cards and inputs sit on top with plain `--color-surface`.
- **Tabular figures everywhere.** `body` sets `font-variant-numeric: tabular-nums`; numeric inputs and table cells are right-aligned (`.num`, `.field__input`, `.data-table__num`).
- **Calculator layout.** `.calc-layout` with `__primary` (area and price; narrowed from area, buyer, price by the primitives work below), `__answer` and `__rest`. One column on mobile in that order, so the answer card comes directly after the first inputs; from 60rem two columns (5fr inputs, 7fr answer) with the answer spanning both rows.
- **Prop contracts** for the primitives are in `src/components/ui/types.ts`. Values are passed pre-formatted as strings, so primitives never format numbers.
- **Token reader.** `scripts/lib/read-tokens.mjs` parses tokens.css into `{ light, dark }` maps and resolves `var()` references, so scripts and tests (contrast checks, the dark-theme e2e check) use the real values instead of copies. Unit tests now also run from `scripts/**/*.test.ts`.

## Page shell (phase 2)
- **Logo "Sun on the sill".** `src/components/Logo.astro` draws the mark on a 24-unit grid: an ink horizon bar (`.logo__horizon`, a 22 x 2 rect at y 17-19), a hi-vis half sun of radius 6.25 centred on the horizon (`.logo__sun`) and three short ink rays at 90 and 45 degrees (`.logo__ray`, 2-unit round-capped strokes). Horizon and vertical ray sit on whole units, so the mark is pixel-crisp at 24px and 48px. The sun has a 1.5-unit outline: ink in light mode, so the hi-vis (about 1.2:1 on concrete) still reads; hi-vis in dark mode, where it already stands out. That outline is the one shell token, `--color-logo-sun-edge`. Props: `size` (mark height, default 32), `wordmark` (default true), `label` (accessible name when the wordmark is hidden), `class`. The wordmark is B612 Bold at `size x 0.5625` (18px beside the default 32px mark), tracked -0.02em. In forced-colours mode the mark is drawn in `CanvasText`.
- **Favicon** (`public/favicon.svg`) is the same geometry with its own colours and a `prefers-color-scheme: dark` block inside the SVG. It has no background square, so it sits on whatever the browser tab colour is.
- **Header.** Logo (linking home) on the left, nav "How it works" and "Sources" on the right; it wraps to two left-aligned rows below about 400px. No header bar or rule: the header sits on the contour background. The current page gets `aria-current="page"` and a 2px underline. Nav links get a small padding, cancelled by a negative margin, so the focus ring has room without moving the text.
- **Footer.** One thin ink rule (`--color-rule`) across the content width, then "This is a model, not financial advice.", links to About and Sources, and the tagline "The maths of moving in." in B612 Mono. All muted text (5.7:1 on light concrete). No second logo, to keep it plain.
- **Skip link.** First tab stop, "Skip to main content", hidden until focused, then a hi-vis pill with ink text at the top left. It targets `<main id="main" tabindex="-1">`; main never shows a focus ring itself.
- **Frame.** `<body class="site">` is a flex column, so the footer sits at the bottom of short pages. `<main>` carries `.container`, so every page's content gets the 1200px max width and gutters without its own wrapper. Prose pages wrap their content in `.prose`.
- **Stub pages** (`/how-it-works/`, `/sources/`, `/about/`) say in two or three plain sentences what each page will hold. They name the planned data sources but give no figures, dates or licences yet; phase 5 fills them in.
- **Contrast guard.** `scripts/check-contrast.mjs` (tested by `scripts/check-contrast.test.ts`, so it runs in `npm test`; also `node scripts/check-contrast.mjs` for a table) measures every token pair the site uses, light and dark, from tokens.css: ink, muted on concrete and surface, on-hi-vis on hi-vis, ink on tag-alt at 4.5:1; buy on surface and concrete at 3:1 (answer numeral and buy line); and the focus pairs at 3:1 (ink edge against concrete and surface in light, hi-vis ring against concrete and surface in dark, hi-vis against the edge in both). Add a row to `CONTRAST_PAIRS` whenever a new text/background combination ships.
- **Rent and hi-vis are never text.** Rent is below 3:1 on light surfaces and hi-vis is about 1.2:1 on light concrete, so neither is measured as a text pair. Instead the same script scans every CSS file, Astro `<style>` block and `style` attribute and fails if `--color-rent`, `--color-hi-vis`, `--color-focus-ring`, `--color-contour` or `--color-buy-fill` is used as `color`, `-webkit-text-fill-color`, or as `fill` in a rule whose selector mentions `text` or `label` (SVG text). Rent and hi-vis remain fine as strokes, fills of shapes and backgrounds. Chart labels for the rent line must be ink. Hi-vis text is banned in dark mode too, where it would pass, to keep one simple rule.
- **e2e for the shell** (`tests/e2e/`): `helpers.ts` holds the page list and shared checks. `pages.spec.ts` (every page: 200, title, one h1, header and footer, no horizontal scroll, no JavaScript, no em-dashes or exclamation marks), `links.spec.ts` (every header and footer link returns 200, nav click-through and `aria-current`), `theme.spec.ts` (light and dark body background, text colour, fixed circle contours and logo colours, read from tokens.css), `focus.spec.ts` (first tab stop is the visible skip link with the ring, skip link moves focus to main, home and nav links show the ring), `smoke.spec.ts` (home placeholder and 404). They use relative paths only, so they also pass against the live site.

### UI primitives (phase 2, primitives)
- **Inputs sit on the page, the answer sits in a card.** On the calculator the fields are surface pills straight on concrete, and the answer (numeral, chart, key numbers) is the only `.card`. That avoids "every block in an identical rounded card".
- **Primary inputs are area and price.** `.calc-layout__primary` holds Area and Property price only; Buyer goes first in `.calc-layout__rest`. The brief's goal is an answer from those two inputs, and the acceptance criteria put the answer card directly after the area and price fields at 360px. This narrows the lead's "area, buyer, price" note.
- **Field edges.** Pill inputs and the segmented track have a 1px `--color-control-edge` (`#777672` light, `#7a7873` dark), quieter than ink but 3:1 against concrete and surface in both themes, so they meet WCAG 1.4.11 without heavy outlines. The pill turns ink on hover; an invalid field gets a 1.5px ink edge plus a bold message with an ink bar, so error state never relies on colour. Asserted in `scripts/theme-panels.test.ts`.
- **Mono where the brief says.** Field labels, segmented legends, units, input values, key numbers, tags, table numbers, chart ticks and the answer numeral use B612 Mono; sentences, hints, segmented options and headings use B612. In B612 Mono the thousands comma takes a full cell (`245, 000`); superseded at integration, see "Narrow punctuation in mono figures" below.
- **Units.** `£` sits at the left of the pill and the value is right-aligned (accounting layout), `%` and `% a year` follow the value.
- **Two-column fields from 26rem of container width.** `.fields` is a container (`container-type: inline-size`) and `.fields__grid` switches from one to two columns at 26rem, so the same markup works in the 5fr calculator column, on tablets and at 360px. `.fields__wide` spans both columns (segmented controls, the disclosure).
- **Sliders sit under their field** (Field default slot). The example has them on price, rent, rate and growth as the brief asks, and the first screen still fits at 1280x800.
- **Chart text is HTML laid over the SVG.** The SVG (viewBox 0 0 100 100, `preserveAspectRatio="none"`, non-scaling strokes) draws lines and fills only; tick labels, the direct "Buy" / "Rent" labels and the "Year 6" label are absolutely positioned HTML using `--x` / `--y` percentages. Text stays at its real size at any width, which a scaled SVG cannot do between 360px and 1280px. Series labels are ink with a short key line in the series colour, so rent orange is never text. The break-even line is hi-vis dashes over a wider dark-ink dash, and its label is ink on hi-vis.
- **Styleguide theme panels.** The styleguide shows every primitive in a pinned light panel and a pinned dark panel. Because tokens live in a media query, tokens.css (primitives section) carries fixed copies `--theme-light-*` / `--theme-dark-*` of each colour, and the page points `--color-*` at them inside `.theme-panel--light/--dark`. `scripts/theme-panels.test.ts` fails if a copy drifts from the real token or a panel misses one. Nothing outside /styleguide/ uses them.
- **DataTable `rowHeader`** (optional, new): renders the first column as `<th scope="row">`. Body cells never wrap; column headings may.

### Integration (phase 2)
- **Narrow punctuation in mono figures.** B612 Mono gives `,` and `.` a full character cell, so "245,000" read as "245, 000" and "4.30" as "4. 30", which looks like two numbers. `src/styles/fonts.css` declares a face, `B612 Mono Punctuation`, that takes only U+002C and U+002E (`unicode-range`) from the self-hosted B612 files, and `--font-mono` lists it first. Digits stay B612 Mono and tabular; every comma and point has the same width, so right-aligned columns still line up. No extra download: it reuses the B612 woff2 files the page already loads.
- **Control edges and reversed-out text are contrast-checked.** `--color-control-edge` against concrete and surface (3:1) and surface on ink (the selected segmented option, 4.5:1) are now rows in `CONTRAST_PAIRS`, in both themes. `npm run lint` also runs `node scripts/check-contrast.mjs` (`lint:contrast`), as well as `npm test` running its unit tests.
- **The styleguide is in the shared e2e page list** (`PAGES` in `tests/e2e/helpers.ts`), so it gets the 200, header and footer, no-scroll, no-JS, copy and link checks at both widths, on top of its own layout spec. It no longer wraps its content in a second `.container`, because `<main>` already carries one.

## Engine contracts (phase 3)
Set by the phase 3 lead before the work split four ways. The types are in `src/lib/types.ts`; this is the summary and the reasoning.

- **Units.** Money in pounds, rates and percentages as decimals (4.3% is `0.043`), years as whole numbers, months as `"YYYY-MM"`. That holds in the engine and in every JSON file under `data/`. Only `format.ts` and the URL (`state.ts`) show percentages as percentages.
- **The engine is pure.** `src/lib/tax.ts`, `model.ts`, `defaults.ts`, `format.ts`, `state.ts` and `schema.ts` have no DOM access, import no JSON and hold no figures. The caller loads `data/*.json`, validates it with `src/lib/schema.ts` and passes it in, so phase 4's island and phase 5's pre-rendered pages share one engine.
- **Calculator state = Selection + Overrides.** `Selection` is `{ areaSlug, buyerType, outlook, nationOverride }`; `Overrides` is the partial set of numeric inputs the user changed. `deriveInputs({ area, areas, rates, defaults, selection, overrides })` turns that into the full `Inputs`, plus `base` (what each field's "Reset" restores) and `provenance` (Local or Typical, with source and month). The URL stores only the selection and overrides, so a shared link re-derives the same result. This replaces the positional `deriveInputs(area, rates, defaults, preset, buyerType, nationOverride?)` sketched in the phase brief: an options object was needed to pass the nation-level figures (for no area or a fallback) and the overrides that the mortgage rate depends on (changing the deposit changes the loan-to-value band, so a link with only `d=` must re-pick the same rate).
- **Derivation order** (documented in `src/lib/defaults.ts`): nation, then price and rent, growth and rent growth (area clamp, then preset), deposit (10% of the final price), fixed defaults and per-nation defaults (survey, Home Report), mortgage rate (from the final loan-to-value and fix length), rate after fix (rate plus the preset's delta), investment return (preset). Each step uses the final, possibly overridden, value of the steps before it.
- **Outlook.** `OutlookPreset` includes `'custom'` for the UI only. The engine and URL carry a `PresetName` (`cautious`, `typical`, `optimistic`). "Custom" shows when any of the four preset-controlled inputs is overridden.
- **Presets as data.** Each preset has `houseGrowth` and `rentGrowth` adjustments `{ add, cap }` applied after the area clamp (growth 0-6%, rent growth 1-6%) and clamped again, a fixed `investmentReturn`, and a `rateAfterFixDelta`. With the table in "Defaults and outlook presets": Cautious growth `{ add: 0, cap: 0.015 }`, rent `{ add: 0, cap: 0.02 }`; Typical both `{ add: 0, cap: null }`; Optimistic growth `{ add: 0.01, cap: 0.06 }`. So Cautious uses the clamped area figure, never a negative one.
- **Mortgage rate pick.** The smallest published LTV band at or above the loan-to-value (60% band for 60% and below, 95% band above 95%), and the nearest published fix length, ties to the shorter fix. `pickMortgageRate` is exported so the UI can show which band was used.
- **Tax result.** `propertyTax({ nation, buyerType, price }, rules)` returns `{ regime, total, bands, reliefApplied, surcharge }`. `bands` is the table actually applied (main, first-time buyer or the Welsh higher-rates table) with the tax per slice. `surcharge` is total minus what a moving buyer would pay, so it reads the same for the English and Scottish whole-price surcharges and the Welsh higher-rates table. `total` is whole pounds.
- **Model result.** `runModel(inputs, taxRules, { sensitivity })` returns `breakEvenYear` (first year-end 1..years with buy wealth strictly above rent wealth), `rentingOvertakesAgainYear`, `series` (year 0 = day one, to `years`), `firstMonth`, `upfront`, `tax`, `selling` (at the horizon) and `sensitivity` (growth 0-5%, then the rate and rate after fix both -1 and +1 point). The model applies the Home Report only when the nation is Scotland, whatever the input holds.
- **areas.json** extends the brief's shape with `schemaVersion`, `generatedAt`, `nations` (nation-level figures for fallbacks and for no area), optional per-area `asOf` (NI prices are quarterly), `rentArea` (the Broad Rental Market Area used in Scotland and NI) and `sample`. Raw figures are stored unclamped; clamping is the engine's job, so the data stays true to the source.
- **Sample data (superseded at integration).** Until the first pipeline run landed, `data/areas.json`, `rates.json` and `sources.json` were labelled samples (`"sample": true` at the top, per-field `sample` lists, series code `"sample"`). The real snapshot replaced them before phase 3 merged, so no committed file is a sample now. Tests that need odd or sample figures use fixtures, never the committed data.
- **Generated JSON is not Prettier-formatted.** The pipeline writes `areas.json`, `rates.json` and `sources.json` with `JSON.stringify(value, null, 2)` and they are in `.prettierignore`. Hand-edited `taxRules.json` and `defaults.json` stay formatted.
- **Scripts are TypeScript run with tsx** (devDependency), so the pipeline imports the same types and validators: `npm run data:refresh` (`scripts/refresh-data.ts`) and `npm run data:validate` (`scripts/validate-data.ts`). tsconfig already allows `.ts` import extensions.

**Calculation conventions** (in `src/lib/tax.ts`, all figures from `taxRules.json`):
- Slice-based tables throughout. The total is **rounded down to whole pounds** (HMRC, Revenue Scotland and the WRA all round down); each band's tax is kept to the penny so the UI can show the working. So £125,001 in England is £0, not 2p.
- **£40,000 threshold:** the surcharge or higher-rates table applies at a price of £40,000 **or more** (the official wording), so £39,999 pays as a mover and £40,000 pays £2,000 (England, Wales) or £3,200 (Scotland).
- **First-time buyer relief** replaces the main table when the price is at or under `maxPrice` (£500,000 counts; £500,001 does not) or always when `maxPrice` is null (Scotland). If a relief table ever cost more than the main table it is not used. `reliefApplied` is true only when the relief actually lowered the bill, so a £100,000 first-time purchase in England shows no relief (both are £0).
- **`bands` in the result** is the full table that was applied (main, first-time buyer or the Welsh higher-rates table), every band listed, with `tax: 0` above the price. For England and Scotland's whole-price surcharges the bands are the main table and the extra is in `surcharge`; for Wales the bands are the higher-rates table. `surcharge` is always total minus a mover's total.
- **England's first-time buyer table** is stored as 0% to £300k then 5% with no upper limit, capped by `maxPrice: 500000`. The lead's skeleton had a redundant third 5% band from £500k; it could never be reached, so it was dropped.
- A zero, negative or non-numeric price pays nothing; the function never throws.
- **Out of scope** (for the explainer's assumptions list): the 2% SDLT surcharge for non-UK residents, companies and trusts, shared ownership, linked or multiple-dwelling purchases, and the refund of higher rates when a previous main home is sold later ("moving" already assumes the old home is sold by completion).
- `parseTaxRules` now also requires at least one source per regime, so a future edit can't drop the citations.

## Model conventions (phase 3)
Written by the model teammate. Code: `src/lib/model.ts`, `src/lib/defaults.ts`; tests: `model.test.ts`, `model.property.test.ts`, `defaults.test.ts`.

- **All five brief model test cases pass exactly; no assertion is skipped or marked as failing.** Payment £1,336.15, first-month owning cost £1,615.32, upfront costs £4,099, break-even years 11, 5, 3, 2, 1, 1 at 0-5% growth, and 10-year wealth £181,199.60 vs £87,864.31 (brief: £181,200 vs £87,864, ±£1).
- **The reference scenario's rent growth is 3.5% a year.** The brief lists every other input but not rent growth ("every other input at its default", and rent growth has no fixed default: it comes from the area). We swept it: 3.5% is the value that reproduces the brief's 10-year figures to the pound under the conventions below, and with it every break-even year also matches (3% gives 13, 5, 3, 2, 1, 1 and £92,512 rent wealth; 4% gives 10, 5, ... and £84,225). The test fixture states `rentGrowth: 0.035` and says why.
- **Monthly order of events** (the spec leaves these open; each choice was checked against the test cases):
  1. At the first month after the fix, the payment is recomputed on the remaining balance over the remaining term at the rate after the fix.
  2. Interest is charged on the balance at the start of the month (annual rate / 12), then the payment is made at the end of the month. The last month of the term clears whatever balance is left (it is fractions of a penny in practice).
  3. Owning cost = payment + maintenance on the home's value at the **start** of the month + (insurance + service charge) / 12 × (1 + inflation)^(whole years elapsed). Start-of-month value is what gives £1,615.32 (£250 maintenance on £300,000); end-of-month value gives £1,615.94. Maintenance is not uprated by inflation because it already follows the value.
  4. Rent = starting rent × (1 + rent growth)^(whole years elapsed), so it steps up on each anniversary.
  5. The home value grows by (1 + g)^(1/12) − 1.
  6. Both portfolios grow by (1 + r)^(1/12) − 1 (the renter's starting portfolio of deposit + upfront costs grows from month 1), then whoever spent less that month invests the difference at the end of the month. Investing before growing moves the 10-year rent wealth to £87,996 (outside ±£1); not growing the starting portfolio in month 1 gives £87,639. Only "grow, then invest the month's difference" matches.
- **"Inflation applies to insurance and fixed fees"** is read as buildings insurance and the yearly service charge / ground rent / factor fees. Selling costs (legal fees, Home Report) are not uprated: uprating the £1,500 selling fee would take about £420 off the 10-year buy wealth, outside the brief's ±£1. The inflation field's source note in `defaults.json` now says "Uprates buildings insurance and the service charge each year".
- **No rounding inside the model.** Everything is full floating point; the UI formats. Tax arrives as whole pounds from `tax.ts`.
- **Deposit is capped at the price** in the model (loan = price − deposit, never negative). With no loan there is no product fee and no mortgage payment. A zero price runs without NaNs.
- **Break-even** is the first year-end (1..years) with buy wealth strictly above rent wealth. **Renting overtakes again** is the first later year-end with rent wealth at or above buy wealth.
- **Series** has one point per year-end from year 0 (day one: buy wealth = deposit − selling costs, rent wealth = deposit + upfront costs) to the horizon. `owningPaid` and `rentPaid` are the totals paid during that year. `selling` is the breakdown at the horizon.
- **Sensitivity** re-runs the loop with growth set to 0, 1, 2, 3, 4 and 5%, then with the mortgage rate and the rate after the fix both moved by −1 and +1 point (floored at 0). These steps are constants in `model.ts` because they are the brief's definition of the rows, not a default the user can change. The re-runs skip the series and stop at the break-even year.
- **Speed.** One run of 40 years with the eight sensitivity re-runs takes about 0.03ms on the build container (the test asserts the median is under 5ms). The loop allocates nothing per month; only the 41 year points are created.
- **Invariants (fast-check, `model.property.test.ts`).** Rent up never makes break-even later; selling costs up never make it earlier; the zero-growth identity holds (0% growth, 0% returns, no inflation, rate after fix = initial rate, horizon within the term, rent set to the first month's owning cost: buy − rent = principal repaid − upfront costs − selling costs at every year-end, to 4 decimal places). These hold over the full UI bounds. **Growth up never makes break-even later holds over realistic ranges only** (maintenance up to 2%, returns up to 8%, which is what the test draws). At the corners of the UI bounds it can fail, because maintenance is a share of the value, so faster growth costs more maintenance, which the renter invests: with 5% maintenance, 15% returns, 15% rent growth, £525 rent and a £15,000 deposit, break-even is year 39 at −3% growth and year 40 at −2%. That follows from the brief's own formulas, so it is documented by a named test rather than "fixed". A 20,000-case random search over the full bounds found no failure; a targeted grid search found this one.
- **deriveInputs provenance.** "Local" only for an area's own price, rent, growth or rent growth (clamping to the brief's 0-6% / 1-6% keeps it local), with the dataset and month (the area's own `asOf` month when it has one, else the file's). Everything else is "typical": a nation figure (fallback or no area, source names the nation, e.g. "ONS Price Index of Private Rents, Scotland average"), a fixed default (source = the field's `source` note in `defaults.json`, month null), the Bank of England rate (a UK figure; source names the fix and LTV band, month = the rates month), and any value the Outlook preset changed (e.g. Cautious capping growth at 1.5%; the source says "adjusted for the Cautious outlook"). Sample placeholder figures get "(sample figure, not real data)" in the source. For Scotland and NI the rent source names the Broad Rental Market Area.
- **Nation override** changes the tax regime and the per-nation defaults (survey, Home Report) but not the area's figures. With no area, the override also picks which nation's average figures are used. A field that falls back uses the area's own nation's figure.
- **Derived values are tidied to 10 decimal places** (`0.041 + 0.01` is stored as `0.051`, not `0.051000000000000004`), so URL state comparisons against `base` and the UI's percentages stay clean.
- **Overrides that are not finite numbers are ignored**, so `deriveInputs` never throws. Clamping to the field bounds is `state.ts`'s job when it reads the URL.
- **`pickMortgageRate`** allows 1e-9 of floating-point slack on band edges, so a 90% LTV computed as 0.9000000000000001 still gets the 90% band. If a fix length lacks the higher bands, it falls back to the largest band published for that fix length.
- **defaults.json** values are the brief's, and every default sits on its field's step. `parseDefaults` now also rejects a null default on any field that is not derived (`DERIVED_INPUT_KEYS` in `types.ts`: price, deposit, rent, mortgageRate, houseGrowth, rateAfterFix, rentGrowth, investmentReturn) and a zero `depositFraction`.

The keys are exported as `SELECTION_PARAMS` and `INPUT_PARAMS`. They are part of every shared link, so **never rename or reuse a key**; add new ones instead.

| `b` | buyer type | `first`, `moving`, `additional` | equal to `defaultBuyerType` |

| `n` | nation override | `eng`, `sco`, `wal`, `ni` | no override |
| `p` | price | pounds, `p=300000` | equal to the derived default |
| `d` | deposit | pounds | " |
| `r` | monthly rent | pounds | " |
| `mr` | mortgage rate | percentage, `mr=4.3` | " |

| `t` | mortgage term | whole years | " |
| `fx` | initial fix length | whole years | " |
| `ra` | rate after fix | percentage | " |
| `pf` | product fee | pounds | " |
| `lb` | legal fees (buying) | pounds | " |
| `sv` | survey | pounds | " |
| `mv` | moving costs | pounds | " |
| `mt` | maintenance | percentage of value a year | " |
| `ins` | buildings insurance | pounds a year | " |
| `sc` | service charge etc. | pounds a year | " |
| `rg` | rent increases | percentage | " |

| `ag` | estate agent fee | percentage | " |

- **Units come from `defaults.json`, not code.** A field whose unit is `percent` or `percentPerYear` is written as a percentage (0.043 is `mr=4.3`), `years` as a whole number, and money as pounds. So a link reads like the form.
- **Precision.** Percentages to 4 decimal places, money to the penny, years whole. Values are clamped to the field's `min`/`max` and rounded half away from zero (in decimal, so 1250.555 is `1250.56`) on the way out and on the way in. That makes `decodeState(encodeState(x))` exact for anything the UI can enter and makes encoding a decoded state stable. Both are fast-check properties in `state.test.ts`.
- **"Differs from the default"** is decided on the written text: an override is left out when it writes the same as `base[key]` (the value its Reset link restores, from `deriveInputs`). Float noise such as `0.045000000000000005` never adds a parameter. The base is per field given the other overrides, so a link with only `d=` re-derives the same mortgage rate (see "Engine contracts").
- **Order.** Selection keys first (`a`, `b`, `o`, `n`), then inputs in `NUMERIC_INPUT_KEYS` order, so the same state always gives the same link.
- **Decoding never throws.** It accepts `?a=leeds`, `a=leeds`, a whole URL or a `URLSearchParams`, and drops the hash. Unknown keys (including `__proto__`, `utm_source`) are ignored. Unknown enum values fall back to the defaults (`o=custom` is the typical preset). Numbers are read leniently with `parseMoney`/`parsePercent` (`p=300k`, `mr=4.3%`), and anything else (`p=abc`, `p=`, `p=1e5`, `p=Infinity`) is dropped. Numbers are clamped to `min`/`max`. An area slug must be in `knownAreas` when that is passed (phase 4 should pass the slugs from `areas.json`), and otherwise must at least look like a slug. When a key repeats, the last valid value wins, so a value appended to a link takes effect and a junk one appended after it is ignored.
- **Not the URL's job:** clamping the deposit to the price, and dropping a `nationOverride` equal to the area's own nation. Phase 4 should normalise those before encoding if it wants the shortest link.

### Formatting (phase 3)
`src/lib/format.ts`: `formatMoney` ("£300,000", pence only with `{ pence: true }`, "+£1,200" with `{ signed: true }`), `formatPercent` (decimal in, "4.30%" by default, `{ decimals: 1, perYear: true }` for "3.0% a year", `{ signed: true }` for "+1%"; the `signed` option is an addition to the phase lead's stub), `formatYears` ("1 year", "6 years", at most one decimal), `parseMoney`, `parsePercent`.
- **Negatives use U+2212** (`MINUS`), before the pound sign: "−£1,200". A value that rounds to zero shows unsigned ("£0", never "−£0"). Output never contains a hyphen-minus.
- **Rounding** is half away from zero on the decimal reading of the number (en-GB `Intl.NumberFormat`), the same both sides of zero.
- **Non-finite values** format as an empty string rather than "NaN" or a throw; the UI decides what to show.
- **parseMoney** accepts an optional sign (hyphen or U+2212, before or after "£", but only one), "£", digits that are either plain or correctly grouped in threes with commas, an optional decimal part, and a `k` or `m` suffix, with spaces around any of those. It rejects badly grouped commas ("3,00,000"), spaces inside the digits ("1 000"), exponents ("1e5"), hex, "Infinity" and trailing words ("300 pcm"). Suffixes are applied in decimal, so "1.15k" is exactly 1150. **parsePercent** takes the same digits with an optional "%" and "a year".

Comparisons skip anything labelled `sample`, so the first real snapshot passed against the samples.
- **"More than 15% month on month"** applies as written to prices and rents (relative change). For rates a relative 15% is meaningless (1.0% to 1.2% is a 20% move) and would fail most months, so rates are compared in percentage points: 10-year growth 1.5 points, rent growth 5 points (local annual rent changes are volatile), mortgage rates 1.5 points (the biggest recent month, April 2026, moved 0.7 points). These still catch unit slips (3.8 instead of 0.038) and broken joins.
- In the last five years of UK HPI, only City of London's price has moved more than 15% in a month (once, in 2021). If a real move trips the check, re-run the workflow by hand with `allow_moves` (or `allow_count_drop` after an ONS boundary change); both turn those failures into warnings in the summary.

**Workflow (`.github/workflows/refresh-data.yml`).**
- Schedule `17 6 20 * *` (06:17 UTC on the 20th, after the mid-month HPI and ONS releases and the Bank's 5th-working-day release) and `workflow_dispatch`. Commits `data/areas.json`, `rates.json` and `sources.json` to `data/refresh-YYYY-MM` (force-pushed, so a re-run in the same month updates it) and opens a PR into `main` with the job summary as its body, or updates the open one. If PR creation is refused it prints a warning with the compare URL. When nothing changed apart from `generatedAt`, there is no branch or PR.
- **Repo setting needed:** Settings, Actions, General, "Allow GitHub Actions to create and approve pull requests". Without it the run pushes the branch and prints the compare URL.
- **PRs opened with `GITHUB_TOKEN` do not trigger other workflows**, so CI will not run on the refresh PR by itself. The refresh job therefore copies the new files into `data/` and runs `npm test` (which validates every data file and runs the engine tests) and `npm run build` before committing. Closing and reopening the PR also triggers CI.
- Push to `data-test/**`: dry run. Same fetch, build, checks, tests and site build, the summary, and the files as an artifact (`data-<run id>`); no PR. It also force-pushes the files and summary to `data-snapshot/<name>`, because the build container cannot download artifacts (they redirect to Azure blob storage, which its proxy blocks) but can `git fetch`. The first real snapshot in `data/` came from `data-snapshot/refresh` (run 38421635252).
- Permissions: workflow default `contents: read`; the job gets `contents: write` and `pull-requests: write`. Checkout uses `persist-credentials: false` and pushes pass the token explicitly. Action versions as in "Tooling (phase 1)".
- Downloads are kept in `data/raw/` (gitignored); `npm run data:refresh -- --offline` rebuilds from them without the network.

### Area and nation pages (phase 5, areas teammate)
- **"Typical assumptions" is spelled out** on area and nation pages from `defaults.json` (buyer type, deposit share, fix length, the typical investment return and the horizon), with the area's own rate, growth and rent change on area pages, so "typical" is never a vague claim.
- **The "middle answer"** for a nation is the lower median of its areas' break-even years at typical assumptions, counting "no break-even" as later than any year.
- **Possessives always take 's** ("Wales's", "England's"), one rule with no exceptions in generated copy.
- **Price-to-rent** is shown as "Price in years of rent" (price divided by 12 months of rent), a plainer label than "price-to-rent ratio".
- **Related areas** are the six closest by average price in the same nation, shown in a table with the current area in its place (bold, `aria-current`), dearest first, each with its own break-even.
- **Fallback figures** carry a "*" with a visually hidden "({Nation} figure)" and a note under the table, so the table stays aligned and screen readers still hear where the figure comes from.
- **Area tables under 30rem** use 12px figures and tighter gutters, so four columns fit at 360px with no sideways scroll, and "2 years" never splits across lines.
- **Break-even cells** read "N years" or "None in 25 years", matching the island's sensitivity copy.

**Where the island's weight was, and what moved.** `npm run analyze` showed no `preact/compat`, no JSON and no third-party code: all 61.8 KB was our own, so trimming meant not loading what the first render does not need, plus two real cuts.
- *Deferred chunk* (`src/components/calculator/later.ts`, `deferred.tsx`): the chart and its geometry, the share row, the advanced panel, the waiting card's reserved space (`CardGhost`) and the sections under the card (`More.tsx`: sensitivity, breakdown, how this works) load with `import()` the moment the island's module runs, in parallel with the data. They are still server-rendered, so nothing is missing from the page while they load. Each sits in a `Hold` boundary: a part whose code has not arrived throws the pending import, and Preact keeps its server-rendered DOM node (core behaviour for a promise thrown during hydration) until `Hold` renders it again. If nothing changed meanwhile it hydrates in place; if the calculator moved on (someone typed), it renders afresh in the same spot, so no stale attribute survives. `data-hydrated="true"` now means every part is live, deferred ones included, so tests and scripts never act on a static part. A link that names an area (`/?a=leeds`) waits for the chunk as well as the list before showing the answer, so the chart arrives with it and nothing moves. If the chunk fails to load the parts stay as rendered (static) and the rest of the calculator works.
- *Copy split*: the sensitivity tables, tax name and notes and the chart summary moved unchanged from `copy.ts` to `src/lib/copy-details.ts` (only deferred parts use them); `DataTable` is imported from `ui/DataTable` rather than the `ui` barrel, which would otherwise pin it in the island chunk.
- *Analytics*: `track()` reads `PUBLIC_GOATCOUNTER_CODE` into a constant, so a build without it reduces to an empty function and the rest of `analytics.ts` drops out (1.1 KB). With the code set the island is 42,996 B, still under the limit.
- *The area list's validator* (`parseAreaList`) loads with `import()` alongside the list fetch; nothing needs it before the list arrives.
- *Not island, but total*: `@astrojs/preact` lazy-loads `@preact/signals` for signal props, which we never pass; a client-only resolve stub in `astro.config.mjs` (`noSignalProps`) removes its 7.8 KB chunk and throws if a signal prop is ever added. Preact (core, hooks, JSX runtime) now has its own `preact` chunk (rolldown `codeSplitting` group, client build only) so the island's chunks hold only our code.
- `scripts/check-budget.mjs` now also holds every island to **45 KB** (`--max-island-bytes`, `ISLAND_BUDGET_BYTES`): for each `<astro-island component-url>` in the built HTML it adds up the component chunk and every chunk it imports statically, leaving out the framework chunks (`preact`, Vite's preload helper) and listing `import()` chunks as deferred. A static import of `later.ts` anywhere would pull it back into the island and fail CI. Unit tests: `scripts/check-budget.test.ts`.

The rest of the island is the engine (model, tax, defaults, state, format), the inputs and the answer card, which the first render and the first change both need; deferring the URL decoder or the inputs would trade a working calculator for bytes, so I stopped here.

**Shared data: one JSON file, not a JS chunk.** The island's defaults, tax rules, rates, nation figures and old-slug aliases are now `dist/data/calculator.json` (10.5 KB, 3.1 KB gzip; `src/pages/data/calculator.json.ts`), validated at build. Pages render `CalculatorIsland.tsx` with `links={calculatorLinks()}` (and `initialArea` on area pages); the island props are now about 600 characters. Why JSON: it does not count towards the 100 KB JS budget (as a JS chunk the data would have taken total JS to about 91 KB and left a11y work no room), it parses with `JSON.parse` rather than as script, and it matches how the area list already arrives. How it reaches the island (`island-data.ts`):
- build: `calculator-data.ts` registers its loader with `provideIslandData`, so the server render reads the data synchronously and every page's HTML still carries the whole answer, chart, key numbers, sensitivity and breakdown without JavaScript;
- browser: `Base.astro` preloads the file (`preloads` prop, `as="fetch" crossorigin`), so it downloads alongside the island's JS; `Hold` keeps the server-rendered calculator as it is until the data is in, then it hydrates in place. A failed request retries after 1 s and 4 s, then the page simply keeps its static answer.
- the URL carries the first 10 hex digits of the file's SHA-256 (`?v=`), so a page always asks for the data it was built with once caches turn over, while the file keeps a stable name so a page cached from before a deploy still finds it.

**HTML: collapsed content renders when it opens.** The Preact `Disclosure` primitive renders its body the first time it opens and keeps it afterwards (the summary's click, `toggle`, or a native open before hydration all fill it before the next paint). That is the advanced panel (17 or 18 fields, about 20 KB of every page) and the year-by-year table (about 7 KB). The chart's visually hidden table renders once the chart is live (3.4 KB); the one-sentence chart summary stays in the HTML. Once rendered, markup, ids and test hooks are unchanged. Trade-off: with JavaScript off, the year-by-year table and the advanced panel open empty (the advanced fields do nothing without JavaScript anyway); the answer, key numbers, chart drawing and summary, sensitivity and breakdown are all still in the HTML, which `tests/built/answers.test.ts` and the e2e JavaScript-off tests check. Tests that read inside those disclosures now open them first (`openDisclosure()` in `tests/e2e/calculator-helpers.ts`): `nations.spec.ts`, `reference.spec.ts` and `share-url.spec.ts` (its `snapshot()` opens both, so a copied link is still compared field by field and year by year).

**CSS and fonts.**
- *One stylesheet instead of critical CSS.* Inlining was measured against the HTML target: the calculator fills the first screen at both widths, so "critical" CSS is most of the 32 KB, and inlining it would put every area page back over 45 KB and stop the 362 pages sharing one cached file. Instead the calculator's stylesheet now joins the shared one (`Base.astro` imports `calculator.css`): one render-blocking request of 6.5 KB gzip, cached across every page. Lighthouse's render-blocking estimate fell from 520-580 ms to 80-150 ms on mobile (what one external stylesheet costs on simulated slow 4G) and to 0 on desktop; on this branch FCP on mobile went from 1.14 s with two stylesheets to 0.84 s with one, and a desktop CLS of 0.005 left with the second stylesheet. Pages without the calculator download 9.5 KB more CSS than before, once. The calculator's selectors are scoped (`.calc-*`, its own components) except a few that refine the shared primitives (`.answer`, `.chart__*`, `.field__*`); only the noindex styleguide uses those primitives outside the calculator, and its example is checked by `styleguide.spec.ts`. The one rule that changed its layout, the answer note's reserved lines, is now scoped to `.calc-card` in `results.css`.
- *Fonts.* `fonts.css` now declares the four B612 / B612 Mono faces itself, woff2 only (@fontsource's CSS also listed a .woff per face that no supported browser fetches; those files are no longer built), and `Base.astro` preloads the four woff2 files on every page, so they arrive with the stylesheet rather than after it. `font-display: swap` stays, so slow fonts never hide text. Lighthouse no longer lists a font among layout-shift culprits. The `?url` font imports sit after the stylesheet imports in `Base.astro`: Astro orders a page's CSS by import order, and with them first the shared stylesheet landed after the content pages' inline styles and overrode them (the How it works tables overflowed).

**Lighthouse in CI.** `npm run lighthouse` (`scripts/lighthouse.mjs`) serves `dist/` with `astro preview` and runs Lighthouse 13 on `/` and `/rent-vs-buy/leeds/`, mobile and desktop, three runs each. It fails unless, for each page and form factor, the **median** of the three runs scores 95+ in performance, accessibility, best practices and SEO, and the median run (Lighthouse's `computeMedianRun`) is within the stable metric limits: mobile LCP 2,500 ms, TBT 200 ms, CLS 0.1; desktop LCP 1,200 ms, TBT 100 ms, CLS 0.1. It writes `lighthouse/summary.md` (a table with FCP, LCP, TBT, CLS and the render-blocking estimate), `summary.json` and the median runs' HTML reports, and appends the table to the job summary. CI runs it after the e2e suite (`ci.yml`, reports uploaded as the `lighthouse` artifact; job timeout raised to 35 minutes). The deploy workflow's `live` job runs it once against the live site with `--url "$LIVE_URL" --report-only` (`continue-on-error`, `lighthouse-live` artifact): GitHub Pages and the runner's network make those numbers noisier, and CI has already asserted the thresholds on the same build. Variance: the baseline saw a single mobile run of the Leeds page at 94 (TBT 241 ms) among 99-100s; the median of three plus metric limits with headroom is the guard against that, and the bar is not lowered. Main-thread work is also smaller now (about half the server-rendered markup to hydrate, and the deferred parts hydrate in a later task). If CI runners still prove flaky on the performance score, the honest next step is five runs, not a lower threshold.
